# Следующая задача агента B: валидатор контракта v1

Твой результат на 2f9f396 принят. Координатор повторил 933 статические проверки. Перед работой получи актуальную origin/main в своей отдельной копии; используй новую ветку agent-b/contract-validator, не старую ветку DRAFT. Если имя уже занято, изучи состояние и не сбрасывай ветку. Общую папку ведущего не переключай.

Прочитай PROJECT_STATE.md, docs/REVIEW_AGENT_B_01.md, docs/CONTRACT_V1.md и fixtures/synthetic_cases.json. Источником формата теперь является CONTRACT_V1.md, а не твой исторический DRAFT. Особенно проверь user_edits, ручные уточнения и границы структурной/семантической проверки.

Цель: реализовать общий структурный валидатор и проверяемые детерминированные ограничения, без LLM, ASR, Streamlit и экспорта. Оценка 60–120 минут, затем отчёт. Это отдельное разрешение координатора изменить contracts.py, ранее зарезервированный за ним.

Разрешены только:

- docs/agent-b/IMPLEMENTATION_REPORT.md

Канонические fixtures, спецификацию, README, PROJECT_STATE.md и зависимости не меняй. Отрицательные и дополнительные случаи создавай в памяти тестов из копий fixtures. Если спецификация неоднозначна, опиши конкретный пример и предложенное правило в отчёте; не меняй её молча.

Сначала выясни, есть ли на твоём компьютере рабочий Python и какая версия. Не фиксируй минимальную поддерживаемую версию проекта от имени команды. Используй стандартную библиотеку, без pip install и скачивания моделей. WindowsApps/python.exe сам по себе не подтверждает наличие Python. При отсутствии рабочего интерпретатора подготовь код и тесты, честно отметь их незапущенными и сообщи координатору; не имитируй PASS.

В contracts.py реализуй:

1. SCHEMA_VERSION = "qonimai.analysis.v1".
2. validate_transcript(transcript) -> list[dict]: ошибки {code, path, message} без исходного текста и чувствительных значений в сообщении.
3. validate_analysis(transcript, analysis) -> list[dict]: структура оболочки и результата, ссылки, исполнители, авторы, даты, уточнения, user_edits.
4. validate_snapshot(transcript, analysis) -> list[dict]: сочетание проверок и совпадение revision/source_revision для успешных результатов. Не устанавливает пользовательское подтверждение.
5. validate_export(transcript, analysis, reviewed_revision) -> list[dict]: отдельные запреты NO_CONTENT, STALE_ANALYSIS, REVIEW_REQUIRED; разрешение неизвестных полей с корректными уточнениями после просмотра. Error-результат анализа экспортировать нельзя.

Валидаторы не меняют входные объекты, не читают сеть/аудио, не обращаются к модели. На обычном невалидном JSON-совместимом входе возвращают ошибки вместо traceback. Ошибки приложения и конфигурации не выдавай за корректный вход. Обработку произвольного неразбираемого JSON-текста оставь будущему адаптеру модели.

Обязательны: строгие типы (bool не int), ключи, непустые строки, конечные таймкоды, уникальность и регистр id, реальные даты, допустимые null, соответствие confirmed/имени, source-ссылки, автор в доказательствах, причины уточнения и их взаимоисключение, обязательные массивы, ветви ok/no_speech/error, отсутствие мутации аргументов. Перекрытие голосов разрешено.

user_edits проверяй по разделу 5.1: ссылки, одна запись на объект, исходный объект, точные changed_fields, разрешённые изменения, reason, исключение для вручную заданного срока. Схема не может доказать, что пользователь действительно нажал кнопку; создание журнала только после действия пользователя обеспечит UI. Валидатор не должен утверждать, что автоматически проверил истинность всех фактов пересказа.

Календарные проверки: полная дата, «завтра» при известном контексте, границы года/месяца, неизвестный контекст. IANA-зона должна проверяться по настоящей базе часовых поясов, не через жёстко заданные +05:00. Если на Windows нет базы tzdata для zoneinfo, это зависимость среды: явно отрази ограничение/ошибку в отчёте, не подставляй UTC и не устанавливай пакет молча. Допустимо запросить у координатора добавление tzdata в будущие зависимости; успешные проверки зоны выполняются только при наличии базы. Сообщи, какие проверки реально прошли и какие заблокированы средой.

Тесты — unittest. Проверь все 16 canonical cases (включая ручное уточнение), затем отрицательные варианты: неизвестные поля, неверные типы, bool в числах, NaN, дубликаты, отсутствующие ссылки, неверные даты, неверная зона/смещение, устаревшая версия, отсутствие просмотра, сломанный журнал правок, попытка скрыть изменение due_text. Отдельно разреши экспорт NO_DUE после просмотра и запрети NO_SPEECH. Для сравнения саммари не требуй дословного совпадения текста модели.

Команда из корня при наличии рабочего Python:

```text
python -m unittest discover -s tests -p test_contracts.py -v
```

Подставь обнаруженную команду/путь интерпретатора под свою ОС. Не называй эти тесты проверкой ASR, модели анализа, реального DOCX или offline-цепочки.
