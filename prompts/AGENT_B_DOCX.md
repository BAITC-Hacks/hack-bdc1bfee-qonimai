## Цель

Реализовать и проверить участок: синтетический согласованный снимок → validate_export → настоящий DOCX. Это пока не сквозная обработка аудио и не результат модели. Оценка 90–150 минут; при проблемах рендера сообщи о блокере после 20 минут диагностики, продолжая независимые тесты содержимого.

Разрешены только:

- export_docx.py;
- tests/test_export_docx.py;
- examples/__init__.py;
- examples/export_fixture.py;
- docs/export.md;
- docs/agent-b/DOCX_REPORT.md.

Не меняй contracts.py, analysis/, общие fixtures, спецификацию, README, PROJECT_STATE.md, существующие тесты и зависимости. Если потребуются изменения, предложи их в отчёте. Сгенерированные документы/PNG/PDF/окружения/веса не коммить. Для промежуточных файлов используй рабочую папку или временную директорию; для отдаваемого документа — разрешённую твоей средой папку outputs.

Если доступен навык documents, используй его для контрольных DOCX, включая предписанные подготовку и визуальную проверку. Разрешай пути bundled Python/Node/библиотек через инструменты среды. ## Функция

```text
export_docx(transcript, analysis, reviewed_revision, target_path) -> ExportResult
```

Сначала вызвать contracts.validate_export. При ошибке не создавать и не изменять целевой файл. Возвращать `{status: "error", data: null, error: {code, message, retryable}}`. Сохраняй смысл первичных причин: ошибка входа/базы/структуры, STALE_ANALYSIS, NO_CONTENT или REVIEW_REQUIRED. Сообщения фиксированные, без транскрипта, исключения и чувствительного пути. Код при нескольких причинах выбери детерминированно и опиши порядок в docs/export.md.

При успехе вернуть `{status: "ok", data: {path, source_revision}, error: null}`. path — действительный локальный путь готового файла. source_revision соответствует экспортированному снимку. Сеть не используется. Поля входа не менять. Отсутствующий пользовательский просмотр не проставлять автоматически внутри экспортёра.

Путь должен обозначать локальный .docx; URL не поддерживаются. Не создавай произвольные отсутствующие родительские каталоги скрыто: пусть вызывающая сторона выбирает/создаёт папку. Ошибки записи — EXPORT_FAILED. Сначала создай временный файл в том же каталоге, затем замени целевой при полном успехе; при сбое убери только собственный временный файл. При неудаче не порти ранее существующий целевой документ. Не печатай путь и содержимое в логах. KeyboardInterrupt/SystemExit не подавлять.

## Содержимое DOCX

1. Понятный заголовок «Протокол совещания». Дата/часовой пояс из meeting; неизвестное так и отметить. Не подставлять сегодняшнюю дату вместо даты записи.
2. Подтверждённые участники. Неподтверждённого говорящего обозначать как спикера, его подсказку имени не выдавать за установленную личность.
3. Саммари, принятые решения и поручения. Отсутствие поручений прямо обозначить; документ всё равно экспортируется, если есть речь.
4. У поручения показать описание, исполнителя, исходный срок, нормализованную дату, необходимость уточнения/причины и ссылки на подтверждающие реплики. Автора реплики не подставлять исполнителем. Неизвестные значения отображать понятными словами, не строкой null.
5. Ручные изменения выделять «Уточнено пользователем»: актуальное значение, исходное значение и reason. Для всех target_type из user_edits сохранять различие с извлечёнными фактами. Не скрывать отсутствовавший исходный срок после ручного задания даты.
6. Приложение с полным актуальным транскриптом: порядок, номера/идентификаторы реплик для ссылок, таймкоды, подтверждённый говорящий, текст без потерь. Казахские символы, переносы и знаки сохранить.

Оформление простое и читаемое: встроенные стили заголовков, чёрный текст заголовков, основной текст примерно 11–12 pt, без декоративных блоков. Не создавай слишком широкую таблицу с мелким текстом: подробные поручения можно оформить последовательно. Для таблиц — перенос текста, повтор заголовка на новой странице, без фиксированной обрезающей высоты строк. Не пытайся уместить весь длинный протокол на одну страницу.

## Явно тестовый запуск

examples/export_fixture.py читает только канонические вымышленные данные, выбирает --case и принимает --output. Пример команды из корня:

```text
python -m examples.export_fixture --case USER_CLARIFIED_DUE --output exports/demo_synthetic.docx
```

Каталог exports создаётся пользователем/командой подготовки, .gitignore уже исключает его. Сценарий должен явно выводить «Синтетический пример — модели не запускались». Добавь обязательный CLI-флаг --confirm-reviewed: без него не считать результат просмотренным и не экспортировать. Полная команда демонстрации включает этот флаг после просмотра выбранного fixture; это не автоматическое одобрение реального модельного результата.

Подготовь минимум два контрольных DOCX: USER_CLARIFIED_DUE и отдельный длинный синтетический стресс-пример с несколькими поручениями, длинными строками и символами Ә Ғ Қ Ң Ө Ұ Ү Һ І ә ғ қ ң ө ұ ү һ і. Стресс-данные создавай в тестах/сценарии, не меняя общий fixtures. Текст в CLI/описании и имя файла должны ясно обозначать синтетическое происхождение. Не выдавай эти файлы за результат ASR/LLM.

## Проверки

unittest, файловые операции только во временных папках теста:

- Успешный экспорт и чтение DOCX для всех допустимых канонических снимков; NO_SPEECH запрещён.
- Открытие файла через python-docx и проверка текста в paragraphs и tables либо document.xml: имена, все символы, полный транскрипт, даты, порядок, ссылки, причины и ручные изменения.
- NO_DUE/UNKNOWN_ASSIGNEE/NO_TASKS экспортируются после просмотра с честными пометками.
- Устаревший source_revision, отсутствующий reviewed_revision, неправильные ссылки и модельный error не создают файл и не портят существующий.
- Ошибки пути/записи возвращают EXPORT_FAILED; частичный файл не выдаётся как готовый. Контролируемо имитируй сбой сохранения; не меняй системные права и не исчерпывай диск.
- Отсутствие мутации входов, утечки данных в ошибках/логах. Не переносить код проверки из contracts.py внутрь экспортёра.
- После программных проверок отрендерить два контрольных DOCX и просмотреть ВСЕ страницы. Извлечение XML не заменяет визуальную проверку. Если рендер не выполнен — это открытый критерий, не PASS.

Команды из корня через рабочий интерпретатор:

```text
python -m unittest discover -s tests -p test_export_docx.py -v
python -m unittest discover -s tests -p test_*.py
```

Не приписывай этим тестам качество моделей или сквозной offline-запуск. В docs/export.md опиши установку, вызов, путь к тестовому сценарию, ограничения. В DOCX_REPORT.md укажи базовый SHA, среду/версии, команды, тесты/пропуски, способ визуальной проверки и число просмотренных страниц, пути к двум локальным синтетическим образцам, нерешённые проблемы. Коммить только шесть разрешённых исходных файлов, обычным push отправь свою ветку, верни SHA. main не меняй.
