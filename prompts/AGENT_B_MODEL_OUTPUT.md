## Задача и границы

Реализуй `parse_model_output(raw_text, transcript) -> AnalysisResult` в analysis/model_output.py. Это локальная проверка строки, которую в будущем вернёт модель. Она НЕ выполняет анализ, не вызывает модель, не читает сеть/файлы и не подставляет fixtures вместо результата. Оценка 45–90 минут.

Разрешены только:

- analysis/__init__.py — минимальный пакет без побочных действий;
- analysis/model_output.py;
- tests/test_model_output.py;
- docs/analysis.md — документировать только эту готовую часть и ограничения;
- docs/agent-b/MODEL_OUTPUT_REPORT.md.

Не меняй contracts.py, tests/test_contracts.py, общий контракт, fixtures, зависимости, README или PROJECT_STATE.md. Сначала используй доступный рабочий Python с IANA. Если базы нет, её отсутствие является явной ошибкой среды; не подставляй UTC. Установку/загрузку моделей не выполняй.

## Поведение

1. Проверить transcript через validate_transcript. Некорректный вход → оболочка error с INVALID_INPUT; отсутствующая база → TIMEZONE_DATA_UNAVAILABLE. Сообщения фиксированные, не копируют текст и значения входа. При этой ошибке не обрабатывать модельный ответ.
2. raw_text должен быть строкой. Пустая/пробельная строка → EMPTY_MODEL_OUTPUT. Другой тип → INVALID_MODEL_OUTPUT.
3. Принимается один JSON-объект AnalysisResult по контракту v1. Допускаются пробелы до/после. Markdown-ограждения, комментарии, произвольный текст вокруг объекта и несколько объектов запрещены: INVALID_MODEL_JSON. Не извлекать JSON поиском фигурных скобок и не чинить его вторым облачным запросом.
4. Строгий JSON: отвергать дубликаты ключей на любом уровне, NaN/Infinity, синтаксические ошибки и необрабатываемую глубину как INVALID_MODEL_JSON. Корректный JSON, не являющийся объектом требуемой схемы, → INVALID_MODEL_OUTPUT. Парсер не должен падать на обычном ошибочном ответе. Не логировать исходный ответ.
5. Сырой ответ модели должен иметь status=ok; для пустого transcript разрешается только структурно корректный no_speech. Модельный status=error отклонить как INVALID_MODEL_OUTPUT: сообщения MODEL_UNAVAILABLE/RESOURCE_EXHAUSTED создаёт адаптер выполнения, а не текст модели. Ошибочный ответ модели не должен попадать в UI как доверенное сообщение.
6. Для успешной оболочки data.user_edits обязан быть пустым списком. Даже полностью валидный журнал ручных правок из модели отклонять. Интерфейс пользователя создаёт такой журнал отдельно.
7. Передать разобранный объект в validate_snapshot. Неверные поля/ссылки/даты/версии → INVALID_MODEL_OUTPUT. source_revision из ответа не заменять текущей версией ради прохождения проверки. Диагностику пользователю выдавать фиксированным сообщением, без вставки raw_text или приватных значений.
8. Успешный результат вернуть без изменения входного transcript. Не ставить reviewed_revision, не придумывать отсутствующие ключи/summary/tasks, не переводить текст и не исправлять сроки самостоятельно.
9. Для ошибок возвращать `{status: "error", data: null, error: {code, message, retryable}}`. Здесь retryable=false: повтор той же строки не исправляет ошибку; решение перезапустить модель/исправить настройки остаётся уровню приложения. Не подавлять KeyboardInterrupt/SystemExit и не использовать безусловный except BaseException.

Проверка no_speech на этой границе означает только согласованность с пустым транскриптом. Отличить настоящую тишину от сбоя ASR обязан аудиомодуль. Эта функция также не доказывает истинность естественно-языковых фактов.

## Проверки

unittest, отрицательные примеры создаются в памяти. Используй все 15 исходных canonical cases с пустым user_edits; шестнадцатый USER_CLARIFIED_DUE должен быть отклонён как сырой ответ модели. Добавь случаи: пустая строка, нестроковый ответ, битый JSON, Markdown, текст вокруг, два объекта, null/массив вместо оболочки, повтор ключей в корне и вложенном task, NaN/Infinity, неверный speaker/assignee/source, неверная дата, устаревший source_revision, model error с вымышленным секретным маркером, ручная правка из модели, слишком глубокий JSON. Проверь отсутствие мутации и утечки маркера в возвращаемой ошибке.

Убедись, что успех валидатора для итоговой пользовательской правки не означает успех parse_model_output для той же правки: это важный отдельный тест границы доверия. Семантическую достоверность и работу модели тестами парсера не объявляй проверенными.

Из корня, используя обнаруженный Python:

```text
python -m unittest discover -s tests -p test_model_output.py -v
python -m unittest discover -s tests -p test_contracts.py
```
