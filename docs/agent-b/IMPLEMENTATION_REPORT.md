## Поведение реализации

- Строгие типы и наборы ключей; bool не принимается как число/версия. Проверяются непустые строки, id с учётом регистра, ссылки, конечные таймкоды, порядок начала реплик; перекрытие допустимо.
- Подтверждение имени проверяется отдельно от speaker_id; исполнитель ссылается на участника, автор присутствует в доказательствах. Участнику не обязательно говорить или иметь speaker_id.
- Неизвестные значения требуют ровно одну причину соответствующей категории; известные значения исключают такие причины. Причины уникальны по code и согласованы с requires_clarification.
- Проверяются ветви ok/no_speech/error. Корректно оформленная ошибка может пройти проверку структуры результата, но экспортировать её нельзя.
- validate_analysis также проверяет корректность входного транскрипта. validate_snapshot дополнительно сравнивает revision/source_revision; validate_export проверяет просмотр текущей версии и запрещает отсутствие речи, устаревший или ошибочный результат. Валидный NO_DUE с просмотром разрешён.
- user_edits сохраняет original, строго проверяет target, допустимые отличия и точный changed_fields. Обход через изменение due_text, автора, id или источников запрещён. Ручная дата проверяется как календарная; исходная нормализация применяется к original. Изменение срока не требует подмены транскрипта.
- Возвращаемые ошибки имеют только code/path/message, используют фиксированные тексты и пути схемы, не включают значения входных полей. Аргументы не меняются; нет обращения к сети, аудио или модели. Невалидные JSON-совместимые объекты возвращают ошибки, а не traceback.

Коды диагностики валидатора: INVALID_INPUT для транскрипта, INVALID_MODEL_OUTPUT для результата, TIMEZONE_DATA_UNAVAILABLE для недоступной базы зон, STALE_ANALYSIS, REVIEW_REQUIRED и NO_CONTENT для запретов дальнейшей работы. INVALID_MODEL_OUTPUT обозначает также структурную ошибку уже отредактированного анализа, а не доказательство происхождения объекта от модели.

## Границы и вопросы координатору

1. **Естественный язык.** Валидатор не доказывает истинность произвольного саммари, реальность назначения, отмены или гипотезы. Он проверяет существование доказательств и детерминированные ограничения; содержательную проверку выполняют анализатор и человек. Порядок поручений по фактической первой постановке нельзя полностью восстановить только из списка ссылок: отдельного указателя на реплику постановки в схеме нет.
2. **Распознаваемые сроки.** Проверяются полные даты YYYY-MM-DD, DD.MM.YYYY, русский день + месяц в родительном падеже + год и казахская форма «2026 жылғы 30 қыркүйек»; «завтра» по локальной дате, «следующая пятница» и распознанные даты без года как неоднозначные. Для других естественных формулировок проверяются календарная корректность due_date, наличие due_text в источнике и причины, но соответствие смысла не объявляется автоматически доказанным. Нужен согласованный список дополнительных формулировок, если команда ожидает более широкий детерминированный разбор.
3. **Происхождение правок.** validate_analysis принимает итоговый объект, включая корректные пользовательские правки. В его сигнатуре нет признака «сырой вывод модели»: будущий адаптер обязан отдельно отвергнуть непустой user_edits модели. UI отвечает за реальное действие пользователя, сохранение первого original, увеличение revision, сброс просмотра и запрет скрытой перезаписи. Один снимок не доказывает всю историю изменений. reviewed_revision проверяется, но не устанавливается валидатором.
4. **Производные поля.** Раздел 5.1 реализован так: правка task должна действительно изменить description, assignee_id или due_date; requires_clarification и clarification_reasons могут измениться вместе с ними. Переписывание только текста причины не считается правкой поручения. Если нужен отдельный пользовательский редактор причин, требуется решение координатора, а не молчаливое расширение.
5. **Незаданные ограничения.** error.code проверяется как непустая строка: таблица в v1 не объявлена закрытым enum. Повторные source_segment_ids не запрещаются отдельным правилом: спецификация требует непустые существующие ссылки, но не объявляет их уникальными. Уникальность id объектов и changed_fields/code причин соблюдается. Если нужен закрытый набор кодов или уникальные ссылки, это изменение спецификации координатором.
6. **Безопасность чужих строк.** Собственная диагностика не копирует входные значения. Схема не может определить, содержит ли произвольный error.message или reason конфиденциальные сведения; адаптер и UI должны соблюдать правила обработки данных. Тесты используют только вымышленный маркер.

Не проверены: ASR, диаризация, модель анализа, достоверность казахских формулировок человеком, UI, реальный DOCX, производительность моделей, чистая установка приложения и сквозная работа без интернета. Google-документы/реальные записи не использовались. Прохождение валидатора не меняет pending языковых примеров и не означает готовность MVP.
