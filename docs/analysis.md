# Проверка сырого ответа локальной модели

Реализована только функция `analysis.model_output.parse_model_output(raw_text, transcript) -> dict`, возвращающая AnalysisResult из CONTRACT_V1.md. Она проверяет готовую строку локально. Модель, извлечение поручений, ASR, UI и DOCX эта функция не реализует и не вызывает.

## Вызов

```python
from analysis.model_output import parse_model_output

# raw_text — строка будущего локального адаптера выполнения модели.
# transcript — объект Transcript v1, уже находящийся в памяти.
result = parse_model_output(raw_text, transcript)
```

Для модульных тестов строку получают через `json.dumps` из вымышленных ожидаемых результатов `fixtures/synthetic_cases.json`. Это проверка формата примеров, а не вывод работающей модели. Функция не читает fixtures, файлы или сеть, ничего не печатает и не сохраняет исходный ответ в лог.

## Порядок проверок

1. Проверить transcript через `contracts.validate_transcript`. При ошибке вернуть фиксированную оболочку error, не разбирая raw_text. Недоступность базы IANA отличается от неверных входных данных; при нескольких проблемах ошибка базы имеет приоритет.
2. Требовать строку. Пустая или состоящая только из пробельных символов строка означает EMPTY_MODEL_OUTPUT; другой тип — INVALID_MODEL_OUTPUT.
3. Разобрать **всю исходную строку** стандартным JSON-парсером со строгими проверками. Допускаются JSON-пробелы до/после: обычный пробел, табуляция, CR и LF. Markdown, комментарии, BOM, произвольный текст вокруг и несколько документов не исправляются и не извлекаются из ответа.
4. Отклонить повторные ключи на любом уровне, включая ключи с одинаковым значением после расшифровки Unicode-escape. Ключи разных регистров различны; допустимость имён дальше проверяет контракт. Отклонить NaN, Infinity, -Infinity и числовую запись вроде `1e999`, которая превратилась бы в бесконечный float. Ограничение глубины декодера или числа цифр целого приводит к INVALID_MODEL_JSON; глобальные лимиты Python не изменяются.
5. Требовать объект результата: `status=ok` для непустых segments, только `status=no_speech` для пустых segments. Модельный `status=error` всегда отклоняется; ошибки запуска модели должен создавать доверенный адаптер выполнения, а не сама строка модели.
6. Требовать `data.user_edits` ровно как пустой список. Отсутствие поля, неверный тип и любой непустой журнал отклоняются. Ручные исправления создаёт UI после действия пользователя.
7. Вызвать неизменённый `contracts.validate_snapshot`. Ошибки схемы, ссылок, дат или source_revision отклоняются. При успехе вернуть разобранный объект без исправления полей, сроков, перевода, добавления саммари, отметки просмотра или смены версии. Входной transcript не меняется.

## Ошибки

Каждая ошибка имеет форму:

```json
{
  "status": "error",
  "data": null,
  "error": {
    "code": "INVALID_MODEL_OUTPUT",
    "message": "Ответ модели не соответствует требованиям к результату анализа.",
    "retryable": false
  }
}
```

| Код | Причина |
|---|---|
| INVALID_INPUT | Транскрипт не прошёл проверку входа |
| TIMEZONE_DATA_UNAVAILABLE | База IANA недоступна при проверке транскрипта/снимка |
| EMPTY_MODEL_OUTPUT | Пустая или пробельная строка |
| INVALID_MODEL_JSON | Ошибка разбора, дубликат ключа, нечисловая константа, числовое переполнение при декодировании либо недоступная глубина/размер целого |
| INVALID_MODEL_OUTPUT | Нестрочный ответ; корректный JSON неверного типа/схемы; запрещённое состояние или журнал; ошибки validate_snapshot, включая устаревший source_revision |

Сообщения фиксированы и не содержат исходную строку, значения транскрипта, исключения декодера или модельное error.message. `retryable=false` означает, что повтор проверки той же строки не исправит её; решение получить новый ответ или исправить среду остаётся приложению.

Обработаны ожидаемые ошибки разбора ValueError (включая JSONDecodeError), RecursionError и OverflowError. KeyboardInterrupt/SystemExit и неожиданные ошибки приложения не маскируются. Лимиты памяти, времени и размера ответа будущего процесса модели нужно задать на уровне адаптера выполнения; здесь нет вызова модели или автоматического повтора.

## Почему проверка модели строже проверки снимка

`validate_snapshot` принимает законные пользовательские правки. Поэтому канонический USER_CLARIFIED_DUE проходит валидатор, но тот же объект в JSON-строке модели отклоняется `parse_model_output`. Это сохраняет различие между услышанным на записи и добавленным пользователем. Запись `original` и объяснение в модельном ответе не доказывают действие человека.

Успех `no_speech` означает только соответствие пустому транскрипту. Настоящую тишину и сбой ASR должен различать аудиомодуль. Успех `ok` не подтверждает смысловую истинность пересказа или всех назначений: применяются ограничения детерминированного валидатора, нужен просмотр человеком. Функция не устанавливает reviewed_revision и сама не разрешает экспорт.

## Проверка разработчиком

Из корня репозитория, в выбранной среде Python с реальной базой IANA:

```text
python -m unittest discover -s tests -p test_model_output.py -v
python -m unittest discover -s tests -p test_contracts.py
```

Зависимость для базы уже определена координатором в requirements-validation.txt. Модуль использует стандартную библиотеку и существующий contracts.py. Отсутствие IANA не заменяется UTC или фиксированным +05:00. Точные результаты, пути интерпретаторов и пропуски текущей проверки приведены в docs/agent-b/MODEL_OUTPUT_REPORT.md.
