## 4. Непереговорные ограничения данных

- Аудио и транскрипты нельзя отправлять во внешние облачные API: ни для ASR, ни для анализа, ни для «запасного» режима.
- Обработка — локальные модели или сервер в закрытом контуре. Пока наличие такого сервера не подтверждено.
- Не проси пользователя прислать реальные записи или транскрипты в ИИ-чат. Для обсуждения кода используй только вымышленные примеры без персональных данных.
- Не загружай реальные данные в GitHub, Live Share, общий терминал, облачную среду разработки или внешний отладчик. Храни их вне общей папки.
- Для демонстрации допустимы смоделированные записи. Реальные данные должны быть анонимизированы, но это не отменяет запрет внешних API.
- Предусмотри уведомление людей о записи и обработке ИИ до записи. Техническая галочка сама по себе не доказывает, что людей уведомили.
- Скачивание открытых библиотек и весов при подготовке среды отличается от передачи данных на обработку. Позже нужен подтверждённый запуск с подготовленными весами без внешнего интернета.
- .gitignore и .vsls.json исключают типовые данные и секреты, но не определяют чувствительное содержимое произвольного файла.

## 7. Как избежать конфликтов

### Если работаешь в той же папке / через Live Share

- Это одна файловая система и один Git index для всех. Разные чаты не создают изоляцию.
- Меняй только файлы, выделенные тебе. Перед записью прочитай их текущее содержимое.
- Не выполняй git switch/checkout, pull, merge, rebase, stash, reset, clean, add, commit или push. Ведущий выполняет операции с общим состоянием Git и публикацию.
- Разрешены проверки status, diff, log и чтение файлов.
- Если в твоих файлах появились чужие изменения, сохрани их; согласуй пересечение, не перезаписывай автоматически.

### Если работаешь в отдельной локальной копии

- Проверь origin: он должен указывать на репозиторий хакатона. Не меняй чужой remote молча.
- Если копии нет, клонируй этот репозиторий через собственную авторизацию. Пароли и токены не передавай в чат.
- Убедись, что папка действительно отдельная. В ней можно создать рабочую ветку `agent-b/analysis-contract` от актуальной main, если это имя ещё не занято другой работой.
- Если ветка уже есть, сначала изучи её; не сбрасывай и не пересоздавай.
- Коммить только свои файлы. Обычный push своей ветки допустим; main не меняй. Передай ведущему имя ветки и SHA для проверки/объединения.
- Не меняй глобальную Git-конфигурацию и не используй чужое авторство. Если имени автора нет, запроси у пользователя сведения для этой машины.
- Ни в одном режиме не используй Force Push и не удаляй чужую работу.

### Шаг B. Подготовь CONTRACT_PROPOSAL.md

В начале поставь статус `DRAFT — не утверждено координатором`. Предложи один простой согласованный формат, не несколько конкурирующих архитектур. Точные названия дополнительных ключей и функции ещё обсуждаются.

Обязательные элементы:

- Transcript: список сегментов с `id`, `start`, `end`, `speaker_id`, `text`; время в секундах от начала записи.
- Таблица speaker_id → имя или null, с явным состоянием подтверждения пользователем. Не смешивай автоматический номер голоса с установленной личностью.
- Дата/время совещания и IANA-часовой пояс передаются явно. Не подставляй автоматически текущую дату компьютера вместо даты записи.
- Для поручения: уникальный id, описание, ответственный или null, исходная формулировка срока, нормализованная дата или null, ссылки на подтверждающие сегменты, requires_clarification. Предложи удобное представление ответственного и причин уточнения.
- Отдельно определён автор реплики; он не является исполнителем по умолчанию. Исполнитель может вообще не говорить в записи.
- Саммари и решения с подтверждением в исходных сегментах; вымышленные решения недопустимы.
- Предложи имена функций и входы/выходы границ ASR/анализа/экспорта. Это только проект интерфейса: никаких импортов конкретной модели или выбранной библиотеки в контракте.
- Опиши отсутствие речи, отсутствие поручений, неизвестного исполнителя, неправильный JSON модели, пустой ответ и недоступную модель как разные состояния.
- Предложи правила повторной проверки после редактирования текста, имён участников, даты совещания и поручений. Исправленный текст должен попадать в экспорт; устаревшие ссылки на сегменты не должны оставаться незамеченными.
- Дай один полный вымышленный пример входа и ожидаемого выхода, без `...` и несовместимых названий полей.

Правила валидации: уникальные id, существующие ссылки, неотрицательное начало, end >= start, корректные speaker_id, допустимые null, строки дат ISO, понятные причины уточнений. Не запрещай пересечение таймкодов разных говорящих: люди могут перебивать друг друга. Семантическая проверка нужна отдельно от корректности JSON.

Не нормализуй неоднозначные выражения вроде «к следующей пятнице» без согласованного правила. Для однозначного «завтра» вычисление зависит от даты совещания в его часовом поясе. Не добавляй выдуманный час, если назван только день.

### Шаг C. Подготовь SYNTHETIC_CASES.json

Это контрольные вымышленные данные и ожидаемые результаты, **не вывод работающей модели**. Пометь это в метаданных файла. Каждый случай содержит id, язык, дату/часовой пояс при необходимости, участников и подтверждённые/неподтверждённые соответствия, сегменты, ожидаемый результат и объяснение проверки.

Подготовь минимум восемь небольших случаев:

1. Русский, два говорящих: один поручает другому действие с явной датой. Автор и исполнитель различаются.
2. Казахский, два говорящих: поручение с известным содержанием. До проверки знающим язык человеком — `language_review: pending`, не выдавать за проверенный эталон.
3. Смешанный русский/казахский: переключение языка внутри диалога; пометка о языковой проверке.
4. Поручение без срока: дата null и видимая необходимость уточнения срока.
5. Однозначное «завтра»: явно заданная дата совещания и часовой пояс; проверь также границу месяца или года.
6. Разговор без поручений: пустой список поручений, саммари только о фактическом обсуждении.
7. Неопределённый ответственный: «Нужно подготовить таблицу»; нельзя назначить автора реплики по умолчанию.
8. Два человека с одинаковым именем или неподтверждённое имя: неоднозначность сохраняется, система не угадывает.

Дополнительно полезны отмена поручения и обсуждение гипотетического действия, чтобы модель не считала их действующими заданиями. Лучше небольшие точные примеры, чем большое количество непроверенных.

JSON должен синтаксически разбираться. Ссылки на сегменты, даты и ожидания должны соответствовать проекту контракта. Саммари оценивается по фактам, а не по буквальному совпадению строки.

### Шаг D. Подготовь ACCEPTANCE_PLAN.md

Таблица: сценарий → вход → ожидаемое поведение → способ проверки → фактический статус. Пока ставь `не запускалось`, если реальный запуск не выполнялся.

Опиши будущие проверки:

- Контракты и семантика поручений на вымышленных транскриптах.
- Короткие смоделированные записи: русский, казахский, смешанный, минимум два говорящих. Нужны эталонный текст и проверка человеком со знанием языка.
- Диаризация и подтверждение имён: отдельно от качества ASR.
- Полная цепочка аудио → сегменты → анализ → редактирование → DOCX.
- Сохранность исправленного текста и казахских символов Ә Ғ Қ Ң Ө Ұ Ү Һ І, а также строчных вариантов; порядок поручений, ответственные и даты.
- Ошибки: неподдерживаемый/пустой файл, нет речи, недоступные веса, повреждённый JSON, нехватка памяти. Не заменять ошибку «готовым» вымышленным результатом.
- Время загрузки и обработки каждого этапа, длительность записи, оборудование, RAM/VRAM, размер/версия модели и режим вычислений. Показать ограничения замера.
- Чистое окружение по README с подготовленными весами и отдельная проверка без внешнего интернета. Не обещать offline только на основании слова local в названии пакета.
- Резерв для демонстрации: ранее выполненный результат или запись экрана, явно обозначенные как сохранённый запуск.

Не выдумывай пороги качества от имени организаторов. Если предлагаешь численные критерии, отмечай их как предложение для согласования.

### Шаг E. Проверь и отчитайся

Для Windows PowerShell, из корня проекта:

```powershell
Get-Content -LiteralPath docs/agent-b/SYNTHETIC_CASES.json -Raw | ConvertFrom-Json | Out-Null
git diff --check
git status --short
```

Успех JSON-проверки — отсутствие ошибки разбора. Дополнительно проверь уникальность id, существование всех ссылок и ожидаемые даты; запиши способ и фактический результат. `git diff --check` проверяет изменения отслеживаемых файлов и не заменяет проверку новых файлов. Не заявляй, что эта команда протестировала содержимое всех новых документов.

На иной ОС используй имеющийся JSON-парсер; не устанавливай тяжёлую среду только ради этой проверки. Если инструментов нет, честно сообщи, что подготовлен проект без выполненной машинной проверки, и дай подходящую команду пользователю.

Не запускай продуктовые тесты, которых ещё нет. Проверенный синтаксис fixtures не означает проверенное качество модели.

## 9. Критерии завершения первой задачи

- Подготовлены все четыре разрешённых файла, они согласованы между собой.
- Проект интерфейса явно помечен DRAFT.
- Контрольные данные обозначены синтетическими; казахский помечен как ожидающий языковой проверки там, где она не выполнена.
- Существуют ожидания для автора/исполнителя, null, относительных сроков, отсутствия поручений и неоднозначности.
- Выполнены доступные проверки; невыполненные перечислены отдельно.
- Изменения ограничены разрешёнными файлами, тяжёлых установок и загрузок моделей нет.
- В REPORT.md перечислены вопросы к координатору и точные предлагаемые изменения общих форматов.

Заверши самостоятельную первую задачу и передай отчёт без запроса формального «продолжать?». До подтверждения контракта не начинай реализацию зависимых модулей. Можно продолжать исправлять собственные примеры и замечания, не затрагивающие общий интерфейс.

## 10. Формат передачи результата

В `docs/agent-b/REPORT.md` и кратком ответе пользователю укажи:

```text
Агент: B
Исходный коммит:
Режим: общая папка / отдельная копия
Статус: черновик / проверено / требуется решение
Что сделано:
Изменённые файлы:
Команды и рабочая папка:
Фактические результаты проверок:
Что НЕ проверено:
Открытые вопросы:
Предложения по общим интерфейсам:
Предлагаемое обновление PROJECT_STATE.md:
Ветка и SHA, если работа шла в отдельной копии:
Следующий независимый шаг:
```

Не утверждай, что координатор получил сообщение автоматически. В общей папке он прочитает файл; между чатами пользователь передаёт краткий отчёт. Одобрение общих интерфейсов должно появиться в PROJECT_STATE.md или явном сообщении координатора, переданном пользователем.

## 11. Что будет после утверждения

После согласования координатор создаст общий contracts.py и fixtures/, выберет зависимости по результатам проверки оборудования и назначит следующую задачу. Тебе может быть поручен модуль локального анализа с теми же форматами, проверкой JSON и подтверждением извлечённых фактов. Это будущая работа, а не разрешение начать сейчас с произвольной LLM.

Первая интеграция проводится рано: участники 2 и 3 начинают с явно отмеченных fixtures, затем подключаются реальные модули. Заглушки не считаются выполненными требованиями. Ошибки исправляем минимально, с точной повторной проверкой; если проблема угрожает сроку, предлагаем реалистичный локальный запасной путь и объясняем его ограничения.

## 12. Финальные требования проекта, которые нельзя потерять

README итоговой версии должен описывать назначение, архитектуру, оборудование, версии, получение моделей, установку, запуск, тестовый сценарий, ограничения и локальную обработку данных. Каждый модуль документирует его автор, сводит участник 3.

До сдачи нужно проверить запуск из чистого окружения и без внешнего интернета, измерить время обработки с указанием оборудования, проверить все три языковых режима и DOCX. Для жюри готовится демонстрация на 3–5 минут: проблема → запись → результат → проверка поручений → экспорт → ценность. Резервный показ честно обозначается как ранее выполненный запуск.
