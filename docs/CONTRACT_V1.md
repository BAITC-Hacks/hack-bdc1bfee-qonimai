# Контракт MVP QonimAI v1

**Утверждено координатором для разработки MVP, 2026-09-23.** Версия: `qonimai.analysis.v1`. Каноническая спецификация — этот файл, контрольные примеры — `fixtures/synthetic_cases.json`. Документы в docs/agent-b/ сохраняются как исходный DRAFT и отчёт; при расхождении действует этот документ. Это утверждение интерфейсов, а не подтверждение реализации или качества моделей. Основание — предложение агента B на коммите 2f9f396 и проверка координатора. Полное ТЗ Google Docs по-прежнему не прочитано.

## 1. Единый вход Transcript

Все перечисленные ключи обязательны. Неизвестное значение записываем как JSON `null`, а пустой список — `[]`. Пустая строка не заменяет неизвестное значение. Неизвестные ключи считаем ошибкой формата, чтобы опечатки не терялись молча. Строковые идентификаторы сравниваются с учётом регистра, bool не является числом таймкода или версии.

| Поле | Тип и смысл |
|---|---|
| schema_version | Строка `qonimai.analysis.v1` |
| revision | Положительное целое; версия согласованного снимка данных, первоначально 1 |
| meeting | `{started_at, timezone}` |
| meeting.started_at | ISO 8601 / RFC 3339 с числовым смещением, например `2026-09-23T10:00:00+05:00`, или null |
| meeting.timezone | IANA-зона, например `Asia/Qyzylorda`, или null |
| participants | Список `{id, name}`: только подтверждённые пользователем участники; одинаковые имена допустимы, id различны |
| speakers | Список `{speaker_id, participant_id, display_name, confirmed}` |
| segments | Список `{id, start, end, speaker_id, text}` в порядке начала реплик |

`start` и `end` — конечные числа секунд от начала записи, `0 <= start <= end`. Пересечения таймкодов допустимы, в том числе у разных голосов. Одинаковое начало не ошибка; при равенстве сохраняем исходный порядок. Все id — непустые строки; уникальность проверяется внутри соответствующего списка и снимка, а не между независимыми совещаниями.

`speaker_id` сегмента ссылается на speakers. Номер голоса не означает установленную личность. Для `confirmed: true` нужны существующий `participant_id` и `display_name`, равный текущему имени участника. При `confirmed: false` поле `participant_id` равно null, `display_name` может быть null или неподтверждённой подсказкой; UI помечает её как неподтверждённую. Автоматически переносить такую подсказку в участники нельзя. Несколько speaker_id могут после ручной проверки относиться к одному участнику: диаризация могла разбить один голос.

Исполнитель может быть в participants, но не иметь реплик или speaker_id. Если реплика содержит только имя, совпавшее у двух участников, id не угадываем. Если личность говорящего неизвестна, создаём стабильный неподтверждённый speaker_id; случайное имя не подставляем.

Дата записи не заменяется системным временем. Смещение started_at должно соответствовать timezone в этот момент; несоответствие — `INVALID_INPUT`. Если дата или зона неизвестны, сохраняем null. Полная явная дата поручения может быть известна и без даты совещания, но относительный срок остаётся неразрешённым.

## 2. Выход AnalysisResult

Общая оболочка: `{status, data, error}`. `status` принимает `ok`, `no_speech`, `error`.

При `ok` и `no_speech`: error = null, data = `{source_revision, summary, decisions, tasks, user_edits}`. source_revision равен revision проверенного входа. summary, decisions, tasks и user_edits всегда списки. Новый результат модели имеет user_edits = []. `no_speech` допустим для корректной записи без обнаруженной речи: segments и все четыре списка пусты. Пустой вывод ASR после обнаружения речи является `EMPTY_MODEL_OUTPUT`, а не доказательством тишины. Непустой транскрипт без поручений возвращает `ok`, tasks = [], содержательное саммари и только реально принятые решения.

Элементы summary и decisions: `{id, text, source_segment_ids}`. Саммари передаёт подтверждённые факты обсуждения. Решение — только явно принятое решение; обсуждение возможности им не является. Каждый элемент имеет хотя бы одну существующую ссылку. Проверять только наличие ссылки недостаточно: её текст должен подтверждать утверждение. Свободный пересказ допустим; дословное совпадение с fixture не требуется.

Элемент tasks:

| Поле | Правило |
|---|---|
| id | Уникальная непустая строка внутри tasks |
| description | Непустое описание конкретного действующего поручения |
| author_speaker_id | speaker_id автора исходной постановки поручения; он присутствует среди подтверждающих сегментов |
| assignee_id | id однозначно установленного исполнителя из participants либо null |
| due_text | Точная исходная формулировка срока из подтверждающего сегмента либо null |
| due_date | Календарная дата `YYYY-MM-DD` либо null; часы и часовой пояс здесь не добавляем |
| source_segment_ids | Непустой список id сегментов; включает постановку, уточнение/принятие, если на них опирается результат |
| requires_clarification | Boolean: true тогда и только тогда, когда есть причины уточнения |
| clarification_reasons | Список `{code, message}`; code стабилен для UI, message понятно объясняет причину по-русски |

Коды причин: `missing_due` (срок не назван), `ambiguous_due` (срок неоднозначен), `missing_meeting_context` (нет даты или зоны для относительного срока), `unknown_assignee` (не назван), `ambiguous_assignee` (несколько кандидатов), `unconfirmed_assignee` (личность не подтверждена). Один код не дублируется в поручении. При assignee_id = null обязателен ровно один из трёх кодов об исполнителе; при due_date = null обязателен ровно один код о сроке. При известном значении причин соответствующей категории быть не должно. Для результата модели due_text = null требует due_date = null и missing_due. Исключение для даты, уточнённой пользователем, описано в разделе 5. Другие неразрешённые противоречия требуют ручной проверки и согласования расширения кодов, а не догадки.

Автор и исполнитель независимы. «Нужно подготовить таблицу» не назначает автора исполнителем. «Я сделаю» разрешается только через подтверждённую связь голоса с участником. Явное обращение к уникальному подтверждённому участнику позволяет назначить его без его собственной реплики. Неподтверждённая подпись голоса сама по себе такого права не даёт.

`tasks` содержит только действующие поручения в порядке первой постановки. Явно отменённое поручение убираем; отмену с обеими ссылками фиксируем в decisions. Условное обсуждение без принятого обязательства в tasks не попадает. История отмен вне текущего снимка пока не проектируется. Извлечённые id не обязаны совпадать с id эталона: будущий тест сопоставляет факты и связи, а не случайные номера.

## 3. Сроки

1. Явная полная дата, например «до 30 сентября 2026 года», даёт `2026-09-30`. due_date означает названный календарный день; включительность «до», время напоминания и точный час не выводятся из него.
2. «Завтра» — следующий календарный день относительно started_at, приведённого к meeting.timezone. Не прибавляем произвольные 24 часа к текущему времени компьютера. Проверяем границы месяца/года. Оригинал остаётся в due_text.
3. «К следующей пятнице», дата без года, конфликтующие сроки без ясной последней правки — due_date = null, `ambiguous_due`. Политику нормализации согласует координатор.
4. «Завтра» при недостатке контекста — due_date = null, `missing_meeting_context`. Неправильный формат даты или несуществующая IANA-зона — ошибка входа, а не пропущенное значение.
5. Если срок не назван, оба поля срока null, причина `missing_due`. Не добавляем фиктивные дату или время.

## 4. Предложение границ модулей

Это утверждённые логические границы модулей; типы Python и зависимости определим после проверки среды. Все результаты должны быть JSON-совместимыми.

| Граница | Вход → выход |
|---|---|
| `transcribe(audio_path, meeting, participants)` | Локальный путь к записи и метаданные → TranscriptResult `{status, data, error}`; data = Transcript при успехе/нет речи. Начальные speakers неподтверждены |
| `analyze(transcript)` | Transcript → AnalysisResult; выполняет структурную и семантическую проверку вывода локального анализатора |
| `validate_snapshot(transcript, analysis)` | Согласованный снимок → список `{code, path, message}`; пустой список означает отсутствие найденных нарушений, не одобрение фактов человеком |
| `export_docx(transcript, analysis, reviewed_revision, target_path)` | Актуальный, проверенный пользователем снимок и локальный путь → ExportResult `{status, data, error}`; при успехе status = ok, data = `{path, source_revision}` |

У экспорта нет status = no_speech. Экспорт пустой записи блокируется с `NO_CONTENT`; поддержка отдельного пустого протокола требует решения команды. Экспорт не запускает скрытый повторный анализ и не получает внешний URL для обработки данных.

При любой ошибке status = error, data = null, error = `{code, message, retryable}`. Сообщение не содержит записи, транскрипта, секретов или внутреннего чувствительного пути. retryable указывает на возможность повтора после исправления причины, а не на автоматический бесконечный повтор. Частичный результат нельзя выдать как успешный.

| Состояние | Ответ |
|---|---|
| Корректная запись с тишиной | transcribe/analyze: no_speech; data с пустыми segments/списками соответственно |
| Разговор без поручений | analyze: ok, tasks = []; фактическое саммари сохраняется |
| Неизвестный исполнитель | analyze: ok, assignee_id = null, видимое уточнение |
| Нулевой файл / неподдерживаемый формат / повреждённый вход | error: `EMPTY_FILE` / `UNSUPPORTED_FORMAT` / `INVALID_INPUT` |
| Неправильный JSON анализатора | error: `INVALID_MODEL_JSON`; валидный JSON с неверной схемой/необоснованными фактами — `INVALID_MODEL_OUTPUT` |
| Пустой ответ анализатора | error: `EMPTY_MODEL_OUTPUT`; не трактуем как отсутствие поручений |
| Модель/веса недоступны | error: `MODEL_UNAVAILABLE` |
| Недостаток памяти | error: `RESOURCE_EXHAUSTED` |
| Устаревший результат / не подтверждена текущая версия | error: `STALE_ANALYSIS` / `REVIEW_REQUIRED` |
| Ошибка записи DOCX | error: `EXPORT_FAILED`; не показывать ссылку на будто бы готовый файл |

## 5. Правки и экспорт

Каждое сохранённое редактирование текста, сегментов, имён/связей, метаданных совещания или поручений увеличивает Transcript.revision; это версия всего снимка для проверки согласованности. Старый analysis.source_revision сохраняется до повторной проверки, reviewed_revision сбрасывается в null. Нельзя просто переписать номер версии и признать старое саммари актуальным.

- Текст, удаление/разделение сегмента: проверить все ссылки, заново проверить факты саммари, решений и поручений. Стабильный id не гарантирует прежнее содержание. При разделении назначить новые id, старые ссылки считать устаревшими. Повторный анализ не перезаписывает пользовательские правки без показа сравнения.
- Имена/подтверждение: заново проверить назначения, особенно «я» и одноимёнцев. Переименование участника обновляет подтверждённые display_name; id сохраняется. Удаление участника/связи делает зависимые назначения требующими проверки, а не автоматически назначенными другому человеку.
- Дата/зона: пересчитать относительные сроки из due_text; проверить смещение. Явные даты сохранить после проверки источника.
- Поручение: проверить исполнителя, дату, причины и подтверждающие ссылки. Исправление ошибки ASR в транскрипте и новое уточнение пользователя — разные действия. Не менять транскрипт ради обоснования нового срока или исполнителя. Уточнения сохранять в user_edits и обозначать в интерфейсе/экспорте как внесённые пользователем. Добавление новых поручений вне записи в v1 не поддерживается.
- После проверки обновить analysis.source_revision до текущей revision; пользователь подтверждает актуальный результат, reviewed_revision = revision. Экспорт требует совпадения всех трёх версий и отсутствия ошибок validate_snapshot.

Неразрешённые уточнения не скрываем: после явного просмотра пользователем экспорт допустим с надписью «Требует уточнения» и причинами, неизвестные значения отображаются «не определён / не указан». Семантическое противоречие, не оформленное как пользовательское уточнение, или битая ссылка блокируют экспорт. DOCX строится из переданного актуального текста и списков, а не исходного кэша; сохраняет порядок реплик/поручений, имена, даты и казахские символы. Эта политика утверждена. Просмотр пользователем не означает, что все сроки и ответственные уже определены.

### 5.1. Происхождение пользовательских исправлений

Каждая запись user_edits имеет ровно поля `{target_type, target_id, original, changed_fields, reason}`. target_type — `task`, `summary` или `decision`; target_id ссылается на существующий объект соответствующего списка. Одна запись на пару target_type/target_id. original — полная копия объекта до первой пользовательской правки в рамках данного результата анализа; без вложенных user_edits. reason — непустое объяснение пользователя. changed_fields — непустой список уникальных ключей, точно совпадающий с различиями между original и текущим объектом. original сохраняется при повторной правке. Если объект полностью возвращён к оригиналу, запись удаляется.

Для task редактируются description, assignee_id, due_date; при этом requires_clarification и clarification_reasons пересчитываются и тоже включаются в changed_fields, если изменились. id, author_speaker_id, due_text и source_segment_ids остаются исходными. Для summary/decision меняется только text. Изменение исходных ссылок или due_text выполняется через пересмотр транскрипта и анализа, а не маскируется ручной правкой.

original проверяется по тем же структурным правилам и ссылкам, что и извлечённый объект. Смысл и исходные сроки проверяются относительно original; ручные отличия не объявляются услышанными на записи. Для даты, добавленной пользователем при отсутствии исходного срока, разрешено due_text = null и due_date != null только при корректной записи user_edits с изменённым due_date. В DOCX показываются исходная формулировка и пометка «Уточнено пользователем», объяснение и актуальное значение. Неизменённые поля остаются основанными на транскрипте.

LLM не имеет права создавать user_edits: непустой журнал в сыром выводе модели — INVALID_MODEL_OUTPUT. Его заполняет только интерфейс после действия пользователя. Модель не может использовать это поле для обхода проверки фактов.

### 5.2. Что доказывает проверка версии

Transcript.revision — версия всего снимка совещания, включая пользовательские исправления анализа. При любом сохранённом изменении увеличиваем её на 1 и сбрасываем reviewed_revision в null. Старый analysis.source_revision не меняется автоматически. Повторная структурная и содержательная проверка либо новый анализ разрешает обновить source_revision; последующее подтверждение пользователем задаёт reviewed_revision. Изменение одного номера без проверки запрещено.

Новый анализ не перезаписывает ручные правки скрыто: сначала сравнение результатов и явное действие пользователя. validate_snapshot проверяет структуру, ссылки, версии и детерминированные правила. Он не является доказательством фактической истинности произвольного пересказа: до экспорта человек проверяет содержание. Отсутствие ошибок валидатора само по себе не устанавливает reviewed_revision.

## 5.3. Решения по спорным случаям

- «Нужно подготовить таблицу» включаем как требующее уточнения поручение, если это конкретная необходимость в текущем обсуждении; автора автоматически исполнителем не делаем. Гипотезы, цитаты и отменённые задания не считаем действующими поручениями.
- Язык интерфейса и саммари первого MVP — русский; текст исходных реплик сохраняется на исходном языке. Поддержка казахского распознавания обязательна и проверяется отдельно. Перевод саммари не должен добавлять факты.
- Полные даты и однозначные относительные сроки нормализуем; дата без года и «следующая пятница» остаются null с уточнением. Не угадываем включительность «до» или час выполнения.
- Экспорт пустой записи блокируется NO_CONTENT; непустой разговор без поручений экспортируется с саммари и надписью «Поручения не выявлены».

## 6. Проверка и полный пример

Структурно проверяем типы, обязательные/лишние ключи, уникальные id, ссылки, конечные таймкоды, реальные календарные даты, существующие зоны, разрешённые null, согласованность подтверждения имён и причин уточнения. Семантически отдельно проверяем фактическое содержание, автора/исполнителя, наличие обязательства, отмену и нормализацию сроков. Синтаксически корректный JSON не доказывает верность результата модели.
